  Google / Email Auth Audit — NextIgnition

  TL;DR — why it "works sometimes"

  The Android native Google Sign-In flakiness is not random — it's deterministic
  per build artifact. Google grants an ID token only when the running app's 
  signing-certificate SHA-1 + package name matches an Android OAuth client in
  the same Cloud project. Your project signs different builds with different
  keys, and only some of those keys are registered. So the same login button
  succeeds or fails purely based on how the APK on that device was 
  built/installed. This will keep recurring until the signing story is fixed.

  The email/password and web Google flows are essentially fine. Apple and a few
  config inconsistencies are landmines worth fixing.

  ---
  1. The root cause: SHA-1 / signing mismatch (Android native)

  Cross-referencing your screenshots against the code:

  Key / cert: Play App signing key
  SHA-1: C5:A9:C1:7F:7C:…:C1:B3
  Where it comes from: Google re-signs every Play install
  Registered in an Android OAuth client?: ✅ Android client 2 (cgh9l2…)
  ────────────────────────────────────────
  Key / cert: A debug keystore
  SHA-1: 79:B5:36:89:9C:…:03:D6
  Where it comes from: one dev machine's ~/.android/debug.keystore
  Registered in an Android OAuth client?: ✅ Android client 1 (7lsj2uk…)
  ────────────────────────────────────────
  Key / cert: Play upload key
  SHA-1: 00:A7:2A:FD:EF:…:D7:96
  Where it comes from: what you sign the AAB with before upload
  Registered in an Android OAuth client?: ❌ not registered anywhere
  ────────────────────────────────────────
  Key / cert: Every other dev's debug keystore

  Where it comes from: local gradlew assembleDebug

  So your release variant is signed with whatever debug keystore is on the
  building machine. Combine that with the table above and you get this outcome
  matrix:

  That is exactly "sometimes works, sometimes doesn't." Production users from
  the Play Store are stable; the flakiness lives entirely in your
  dev/test/sideload builds — which is what you've been testing with.

  This is the issue you must fix to stop recurrence. Changing capacitor.config
  appId / build.gradle namespace did not address it because the package name was
  never the problem — the package (com.nextignition.app) already matches both
  Android clients. The mismatched thing is the certificate.

  Fixes (do all of them)

  1. Register the missing SHA-1s. In the Cloud Console (project auramed-470305),
  add Android OAuth clients (package com.nextignition.app) for:
    - the upload key 00:A7:2A:FD:EF:C4:FA:C7:28:CE:86:54:AA:12:15:A9:CF:21:D7:96
  (so Internal App Sharing / upload-signed test builds work),
    - a shared team debug key (see #2).
    - The app-signing key C5:A9… is already there — keep it; that's what makes
  Play installs reliable.
    - Note Google's own warning in your screenshot: changes take 5 min – a few 
  hours to propagate. Some of your "it started working later" episodes are
  probably this propagation delay, not a code change.
  2. Commit one shared debug keystore to the repo and point signingConfigs.debug
  at it. Today every machine generates its own debug cert, so only one teammate

  3. Add a real release signing config instead of signingConfig 
  signingConfigs.debug. Use the actual upload keystore (kept out of git,

  2. Second flakiness vector: the button can silently disappear

  LoginPage.tsx:10-12 and SignupPage.tsx:40-42:

  const GOOGLE_CLIENT_ID = Capacitor.isNativePlatform()
    ? import.meta.env.VITE_GOOGLE_ANDROID_CLIENT_ID
    : import.meta.env.VITE_GOOGLE_CLIENT_ID;

  On native this value is only used as a truthy gate ({GOOGLE_CLIENT_ID && …}) —
  it's never passed to the plugin (the plugin reads serverClientId from the
  native config). So:

  - If a build is produced without VITE_GOOGLE_ANDROID_CLIENT_ID in its env (CI,
  a teammate's machine, a stale .env), the entire Google button doesn't render
  on the native app — looking like "Google sign-in disappeared/broke."
  - It's also conceptually wrong: you've put Android client 1's ID (7lsj2uk…)
  into a variable that does nothing but gate visibility.

  Fix: on native, gate the button on Capacitor.isNativePlatform() (always
  available, no env dependency) rather than on an env var that may be absent at
  build time.

  ---
  3. Apple Sign-In + package-name inconsistency (a real landmine)

  There are three different bundle identifiers floating around:

  - capacitor.config.json:2 → com.nextignition.gigzsapp
  - build.gradle:4,7 (the real Android package) → com.nextignition.app
  - authService.ts:216 Apple clientId → com.nextignition.gigzsapp
  - backend/.env.example:34 APPLE_CLIENT_ID default → com.nextignition.app
  - backend/.../authController.ts:487 Apple fallback → com.nextignition.gigzsapp

  For Android this is harmless (Gradle's applicationId wins, OAuth clients match
  it). But Apple Sign-In verification breaks if the audience doesn't match the 
  real iOS bundle id. The backend .env.example default and the controller
  fallback disagree (…app vs …gigzsapp), so whether Apple login works depends
  entirely on APPLE_CLIENT_ID being correctly set on Render.

  Fix: decide the real iOS bundle id (whatever Xcode's PRODUCT_BUNDLE_IDENTIFIER
  is) and make these three agree: Apple clientId in authService.ts,
  APPLE_CLIENT_ID on the server, and the controller fallback. Also align
  capacitor.config appId to the truth to remove the trap (a future cap sync /
  Capacitor version could start honoring it for Android).

  - Token-staleness handling is good. authService.ts:147-197 (force-refresh of
  cached/expired native ID tokens, retry on empty) is a solid defensive fix —
  keep it. It was masking a secondary cause (expired cached idToken), but the
